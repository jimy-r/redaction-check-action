# Changelog

All notable changes to this project are documented in this file.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). This file was started during the work toward v1.1.0, so that is the first release it covers. Earlier releases are described in the commit history.

## [Unreleased]

### Fixed

- OpenAI project, service-account and admin keys are reported. The OpenAI pattern matched `sk-` followed by one unbroken alphanumeric run, which is the legacy key shape. Keys that start `sk-proj-`, `sk-svcacct-` or `sk-admin-` break that run at the second hyphen, and their bodies hold `_` and `-`, so every current key shape passed the scan. The pattern now matches those three prefixes with a body of 20 or more characters, and still matches the legacy shape. A prefix named in prose with no key after it is not reported.

## [1.1.0] - 2026-09-28

### Added

- An allow file for values that are safe every time, such as a module path that the `.local` check reads as a host. The new `allow-file` input (default `.redaction-allow`) and `--allow-file` option take one exact value per line. A finding is let through only when the text its pattern matched equals an entry, case and all. Entries shorter than four characters, holding whitespace or holding U+FFFD (what a byte that isn't valid text decodes to) are ignored, the list stops at 200 entries, and each ignored line gets a warning that names the line but never repeats its text.
- In `added-lines` mode the allow file is read from a commit outside the change, for the net diff and every commit in the range alike, so an entry a pull request or push adds lets nothing through until it has landed. A pull request's test merge reads the commit it was built on. Any other range reads the base as it is now, never the merge base. A push to a branch other than the default one reads the default branch's tip, through the new `--allow-ref` option. When that commit isn't in the clone, no allow file is read and a notice says so.
- `all-files` mode reads the allow file as `HEAD` commits it, from `--root` when that's below the top of the repository. It scans that committed copy as the allow file itself, whatever its size, and the working-tree copy too, so a value in an edit not yet committed is reported. A diff on stdin reads the allow file from disk as given, and knows the allow file's own lines by their path in the diff (the new `--allow-path` option, default `.redaction-allow`). The list never applies to a file with the allow file's name, so a secret pasted into the allow file is still reported.
- The log and the job summary report how many matches the allow file let through. The new `--summary-file` option writes the summary, and the action points it at `$GITHUB_STEP_SUMMARY`.
- Each commit in the range is scanned on its own as well as the net diff, on a pull request and on a push alike. A line one commit adds and a later commit removes never shows in the net diff, but the commit that added it is still on the branch, and public once pushed. Such a finding names the commit's SHA, and a later commit that removes the line doesn't clear it. Rewriting the branch without it does. A merge commit contributes only the lines none of its parents had. Every commit is checked against the same allow list, the base's, so an entry one commit adds covers nothing in the next.
- If a shallow checkout hides some of the range's commits, the scanner fetches their history from origin. If any stay out of view it exits 2 rather than scan fewer commits than the range holds.
- Two outputs. `exit-code` is the scan's exit code, set however the step ends. `report` is the path of a file on the runner that holds the scanner's output, the same masked findings the log shows.
- A `skip-scanner-files` input, off by default. `true` skips `redaction_check.py` and `test_redaction_check.py` at the repository root, whose test fixtures are secret-shaped on purpose. Only this action's own repository should set it.
- `base-ref` takes a full commit SHA as well as a branch name. On a push to the default branch, pass `github.event.before`, the commit the push started from. On a push to any other branch, pass the default branch, `github.event.repository.default_branch`, which scans everything the branch adds. The README has both workflows.
- `CONTRIBUTING.md`, with the setup, the test gate and the rules for adding a pattern, and a short `AGENTS.md` that points to it.

### Changed

- The action's Python stays inside the action. Earlier versions put Python 3.12 first on the job's `PATH`, so every later step in the calling job ran on 3.12 whatever the workflow had set up. The job now keeps the Python it had.
- Exit 2 means the scan could not run, and is never a pass, whatever `fail-on` says. It covers a `base-ref` the action cannot use, a checkout without the pull request's head, a ref that git could read two ways and a diff that cannot be computed. Findings still exit 1 under `fail-on: match` and 0 under `fail-on: none`. A missing `base-ref` exited 1 before, and `fail-on: none` was documented as always exiting 0.
- On a `pull_request` event the scan diffs GitHub's test-merge commit against its own first parent, the base commit the merge was built on. That range is the pull request's own change and needs no merge base with the base branch's current tip, so a base that moves while the check is queued cannot break it. Earlier versions fetched the base with `--depth=1`, which marks the fetched tip as a history boundary, and diffed `origin/<base>...HEAD`. Once the base had moved past the pull request's merge commit there was no merge base, and the step failed. If the base branch was force-pushed and no longer contains the commit the test merge was built on, the range widens to the merge base of the base and `HEAD`, so whatever the rewrite dropped but the pull request still carries is scanned.
- A checkout that does not contain the pull request's head, the default checkout on `pull_request_target`, exits 2 with an error that says so, instead of diffing the base branch against itself and passing.
- Files named `redaction_check.py` and `test_redaction_check.py` at the repository root are scanned like any other file unless `skip-scanner-files` is `true`. Earlier versions always skipped them, so a file in a consumer's repository that merely shared one of those names went unscanned.
- Binary media is checked by name only, and only when the file starts with its format's signature bytes. Images, fonts, compressed archives, and audio and video files are covered. Every other file's content is scanned, including one git would have called binary. The diff runs with `--text`, so a NUL byte or a `-diff` attribute no longer hides a text file's lines, and a text file that only has a media name, such as `notes.png`, is scanned too. An uncompressed `.tar` is scanned, since it holds its files byte for byte.

### Fixed

- A `.local.` segment before a config-file extension, as in `settings.local.json` or `docker-compose.local.yml`, is no longer read as an mDNS hostname. The exempt extensions are `json`, `yaml`, `yml`, `toml`, `ini`, `env`, `js`, `ts`, `xml` and `properties`. A `.local` host inside any other file name, such as a key or `.conf` file named after the host, still matches, and so does a `.local` hostname that ends a sentence.
- A runner's git configuration can no longer blank the scan. The diff runs with `--no-color`, `--no-ext-diff` and `--no-textconv`, so `color.ui=always`, a `diff.external` command or a textconv filter cannot put escape codes in front of every line, rewrite the diff or empty it.
- Git's output is read as bytes and split at LF only, and so is a `--diff-file`. A lone carriage return, a form feed or a U+2028 inside an added line is part of that line. Before, it broke the line in two. The text after it lost its `+` and was never scanned.
- Added content shaped like a diff header is scanned as content. Earlier versions read any line starting `+++ ` as a file header, so an added line of that shape was never scanned, and the lines after it were filed under the path it seemed to name. The parser now reads `---` and `+++ ` as a header only before a file's first hunk, tracks each hunk's line counts so a header-shaped line inside them stays content, and ends a hunk early only at a new file's `diff` line or a hunk header. A `+` line past any hunk is still scanned, under an empty path, rather than dropped.
- A path git quotes in a diff header, for a space, a control character, a double quote, a backslash or a non-ASCII byte, is decoded before its name is checked, so a secret-shaped file in such a directory is reported. Left as printed, `"b/caf\303\251/.env"` has no basename that matches `.env`.
- NUL bytes are dropped from a line before matching, so UTF-16 text, which is what PowerShell 5's `>` writes, is scanned. It has a NUL after every ASCII character, and no pattern matched it.
- In `all-files` mode every file is read whatever bytes it holds. A strict decode used to skip the whole file at its first byte that wasn't UTF-8, secrets and all.
- A finding's path that the runner's stdout cannot encode, on a Windows runner's cp1252 for instance, is escaped instead of crashing the report halfway through.

### Security

- A short ref could be shadowed. The action named the base as `origin/<base-ref>`, and git reads that short name as a tag or a local branch called `origin/main` before the branch on origin, with only a warning. A push to a branch named `origin/main` leaves such a local branch in the checkout, and `fetch-depth: 0` brings every tag. With one in place, a push with `base-ref: main` diffed its head against itself and scanned nothing, and a pull request from an older `main`, with a tag at its head, was scanned without its own lines. Released versions up to v1.0.1 diff against `origin/<base-ref>` and are open to the same thing.
- The base is now fetched and passed in full, as `refs/remotes/origin/<base-ref>`, and so is the default branch that a push to any other branch reads the allow file from. A fetch by the short name could also take origin's tag of that name in place of its branch.
- The script refuses a `--base` or `--allow-ref` that could be more than one ref, and a full ref name that isn't there but that git would read as some other ref. The scan exits 2 and names the refs. A full name that exists is read as itself, as git reads it, and a full commit SHA is always that commit.
- Findings are masked with a keyed hash. Each tag is `hmac:` followed by twelve hex characters of an HMAC-SHA256, under a 32-byte key made fresh for each run and never printed. Earlier versions printed twelve characters of an unsalted SHA-256 as `sha256:`. A value with few possibilities could then be recovered from the log alone. Hashing all of `10/8` recovered a masked private IP in about two seconds. The same value still gets the same tag within a run, so repeats line up, but nobody can recompute a tag from guesses, and tags from two runs can't be matched up.
- What the scanner prints into a workflow command is escaped as `@actions/core` escapes it, `%`, CR and LF in a message, and `:` and `,` in a property as well. A file name carrying a newline could end the command, forge a warning and a `::stop-commands::`, and silence every real finding after it. The action escapes the `base-ref` it prints on a failed fetch the same way.
- A `base-ref` that starts with `-` or holds a control character is refused before any git command runs, and the step exits 2. git reads such a value as an option, and `--upload-pack=<command>` runs that command over a file or ssh remote. The script applies the same check to `--base` and `--allow-ref`, and refuses an `--allow-file` holding a control character, since that path is printed on a line of its own.
